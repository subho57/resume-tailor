Tailpipe, a Go-based observability CLI on DuckDB and Parquet, is a good example. It was built to process large volumes of security and cloud log data, and the first thing that broke under real load was memory: naive full-file reads and writes caused out-of-memory failures once log volumes got large, rather than any query-correctness issue. I fixed it by chunking and batching file reads and streaming writes into DuckDB instead of loading everything at once, which also lifted throughput 30% to 1,000+ logs per second and enabled incremental updates.

What I'd do differently now: I'd design the chunked, streaming ingestion path from day one instead of starting with the simpler full-load approach and discovering the memory ceiling under real data volumes — the constraint was predictable in hindsight, and building for it upfront would have avoided the rework.
